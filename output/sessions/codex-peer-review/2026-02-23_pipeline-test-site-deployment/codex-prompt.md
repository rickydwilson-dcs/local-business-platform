## Brief: Pipeline Test Site Deployment Safety

**Date:** 2026-02-23
**Project:** Local Business Platform monorepo
**Note:** This brief is sent to both Claude and Codex independently. Your plans will be synthesised into a final implementation spec. Do not look at `claude-plan.md` before writing your own plan.

### Problem Statement

The ingestion pipeline (`/pipeline.ingest`) generates test sites (`sites/test-<name>/`) to preview themes before promoting them to production. These test sites caused a Vercel deployment failure on `main` (commit `8113c33`) with `ERR_PNPM_OUTDATED_LOCKFILE`.

**Three root causes:**

1. **Lockfile staleness.** Vercel runs `pnpm install --frozen-lockfile` at the monorepo root, which validates against ALL workspace members discovered by the `sites/*` glob in `pnpm-workspace.yaml`. The test sites were merged to `main` without a matching lockfile update, so the install failed before the build started.

2. **CI participation.** Test sites inherit the full `package.json` from `sites/base-template` via `cp -r`, including `build`, `type-check`, `lint`, and `test` scripts. This makes them full Turborepo task participants. Since the pipeline's AI-generated components contain TypeScript errors, Turbo's `type-check` and `build` tasks fail for the test site workspaces, blocking the entire monorepo CI.

3. **Generated code quality.** The component generator (`tools/lib/theme-component-generator.ts`) sometimes emits bracket-notation prop access (`props['post-thumbnail']`) instead of camelCase dot notation (`props.postThumbnail`). A post-generation fixer (`fixBracketNotationProps()`) exists but was added after the atlas/lyra components were generated, so those components still contain the bug. The TypeScript interfaces declare camelCase props, creating a type mismatch.

**What was done to unblock:** Committed the updated `pnpm-lock.yaml`, stripped CI-participating scripts from both test site `package.json` files (leaving only `dev`/`start`/`clean`), pushed through `develop → staging → main`. Vercel deployment now succeeds.

**What needs a permanent fix:** The pipeline itself must prevent this class of failure for all future test sites.

### Goals

1. Test sites generated by `/pipeline.ingest` must never break monorepo CI (`pnpm build`, `pnpm type-check`, `pnpm lint`)
2. Test sites must never cause `ERR_PNPM_OUTDATED_LOCKFILE` on Vercel
3. Generated components must produce valid TypeScript (camelCase prop access matching declared interfaces)
4. The fix must be upstream in the pipeline — not a manual hotfix per test site

### Non-Goals

- Changing the workspace glob in `pnpm-workspace.yaml` (e.g., excluding `test-*` sites) — test sites need to be valid pnpm workspaces for `pnpm install` / linking to work
- Making test sites pass full E2E tests — they are preview artefacts only
- Fixing the already-generated atlas/lyra components (they'll be regenerated or killed)
- Adding test sites to Vercel deployment targets — they are local preview only

### Acceptance Criteria

- [ ] Running `/pipeline.ingest --url <any-url>` produces a test site whose existence does not cause `pnpm build`, `pnpm type-check`, or `pnpm lint` to fail at the monorepo root
- [ ] The pipeline commits an updated `pnpm-lock.yaml` alongside the test site (or the skill instructs the user to do so before pushing)
- [ ] Generated `.tsx` components in `output/ingestion/<theme>/components/` contain zero instances of bracket-notation prop access
- [ ] The `fixBracketNotationProps()` function catches all bracket-notation patterns (including any edge cases the current regex misses)
- [ ] `/pipeline.kill-site` cleans up lockfile state (runs `pnpm install` or instructs user to do so)
- [ ] All changes are covered by automated tests where practical

### Constraints

- **Git workflow:** `develop → staging → main`. Never push directly to `staging` or `main`.
- **MDX-only content:** Content files are MDX with YAML frontmatter, never TypeScript data files.
- **Theme tokens only:** All styling via Tailwind theme tokens (`bg-brand-primary`), never hardcoded hex.
- **pnpm workspaces:** `pnpm-workspace.yaml` uses `sites/*` glob — all sites under `sites/` are workspace members.
- **Turborepo task discovery:** Turbo runs tasks only if the workspace `package.json` has a matching script name. No script = skipped.
- **Vercel deployment:** Runs `pnpm install --frozen-lockfile` then `turbo run build` at root. If lockfile mismatches workspace members, deploy fails before build.
- **Component generation is AI-driven:** The generator sends prompts to Claude Sonnet, so output is non-deterministic. Post-generation fixers and validators are the reliable safety net.
- **`fixBracketNotationProps()` regex:** Current pattern is `/props\[['"]([a-z][a-z0-9]*(?:-[a-z0-9]+)*)['"]\]/g` — only matches lowercase hyphenated keys. May miss PascalCase, underscored, or mixed patterns.
- **Test sites are ephemeral:** Created for preview, killed with `/pipeline.kill-site` and `/pipeline.kill-theme`. They should leave no permanent footprint in CI.

### Relevant Architecture

**Monorepo structure:**
```
pnpm-workspace.yaml          # packages: ['packages/*', 'sites/*', 'tools/*']
turbo.json                    # build/type-check/lint/test tasks, no exclusion filters
sites/base-template/          # Gold-standard template — never modified by pipeline
sites/test-atlas/             # Pipeline-generated test site (atlas theme)
sites/test-lyra/              # Pipeline-generated test site (lyra theme)
packages/themes/atlas/        # Pipeline-generated theme package
packages/themes/lyra/         # Pipeline-generated theme package
tools/analyse-site.ts         # 14-step analysis pipeline
tools/lib/theme-component-generator.ts  # AI component generation + fixBracketNotationProps()
tools/lib/theme-component-templates.ts  # Template utilities, sanitiseSlotName()
output/ingestion/<theme>/     # Pipeline output: analysis, components, example pages
```

**Pipeline flow (simplified):**
```
/pipeline.ingest --url <url> --name <theme>
  → tools/analyse-site.ts (14 steps: screenshots → AI analysis → component gen → theme scaffold)
  → cp -r sites/base-template sites/test-<theme>
  → Rewrite theme.config.ts, globals.css, layout.tsx, package.json (name only)
  → Copy output/ingestion/<theme>/example-pages/app/* → sites/test-<theme>/app/
  → pnpm install (updates lockfile locally)
  → tsc --noEmit (reports errors, doesn't fail pipeline)
```

**Turborepo task participation:** If a workspace `package.json` has a `build` script → Turbo runs `build` on it. If it lacks a `build` script → Turbo skips it. Current hotfix removes scripts; permanent fix should generate the right `package.json` from the start.

**Component generation chain:**
```
AI prompt → raw JSX string → fixBracketNotationProps() → write .tsx file
                                                        → if still has bracket notation → replace with placeholder
```

**`sanitiseSlotName()`** converts `headline-text` → `headlineText` for TypeScript interface props, but the AI body may still emit `props['headline-text']`.

### What a Good Plan Should Cover

1. **Where in the pipeline should the test site `package.json` be trimmed?** Should it happen in `pipeline.ingest.md` (skill spec), in a new utility function, or by creating a dedicated test-site template?
2. **Should the pipeline commit and push, or just instruct the user?** Automated commit risks unintended changes; user instruction risks forgotten steps.
3. **How should `fixBracketNotationProps()` be hardened?** What bracket-notation patterns does the current regex miss? Should there be a second-pass validator that fails loudly?
4. **Should there be a TypeScript validation gate that blocks component files from being written if they contain type errors?** How would this work given the non-deterministic AI output?
5. **What should `/pipeline.kill-site` do about the lockfile?** Running `pnpm install` is correct but slow. Is there a lighter approach?
6. **Should there be a CI-level safeguard (e.g., Turbo filter, workspace exclusion) as a belt-and-suspenders defence?** Or is the `package.json` approach sufficient?
7. **How should the `fixBracketNotationProps()` post-processor be tested?** What test cases cover the known failure modes?
