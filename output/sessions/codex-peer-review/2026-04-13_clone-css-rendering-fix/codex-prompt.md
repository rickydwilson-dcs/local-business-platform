## Brief: Clone CSS Rendering Fix

**Date:** 2026-04-13
**Project:** Local Business Platform monorepo (Next.js 15, Turborepo, pnpm workspaces, Tailwind CSS)
**Note:** This brief is sent to both Claude and Codex independently. Your plans will be synthesised into a final implementation spec. Do not look at `claude-plan.md` before writing your own plan.

### Problem Statement

The platform has a clone-to-theme pipeline that clones live websites (e.g. colorcode.events, a WordPress/Breakdance site), converts the HTML to React JSX components, and produces a theme package for the platform. The pipeline has three stages:

1. **Clone** — wget + Breakdance HTML to JSX converter. Produces high-fidelity clone files.
2. **Extract/Componentize** — Takes clone JSX, extracts header/footer, writes theme page components preserving the original markup.
3. **Strip** — Replaces business-specific content (names, phone numbers, text) with React props to create a reusable template.

Stages 1-3 work correctly. The problem is **rendering the componentized theme in a Next.js site**. The clone JSX uses Breakdance CSS classes (`bde-section-17-100`, `bde-div-18-109`, `.breakdance`, `.callout`, `.graphic`, etc.) whose rules exist in 53 downloaded CSS files. Getting this CSS to load in the Next.js/Tailwind pipeline has failed every way tried so far:

**Failed attempts:**

1. Concatenating all 53 CSS files into theme `globals.css` — Turbopack's CSS parser rejects complex selectors, inline SVG data URIs, and minified mega-lines in several files (`rsvp.css`, `square.css`)
2. Filtering to 26 essential Breakdance files — `global-settings.css` has `url(icons/eye.svg)` relative path that Turbopack tries to resolve as a module import
3. `@import "../theme-system/dist/base.css"` generated by extract-theme — this file does not exist (working themes don't use this import at all)
4. Removing `@tailwind base;` and `@tailwind components;` from site globals.css — still no layout rendered
5. The `@tailwind base` Preflight reset conflicts with Breakdance's typography, heading sizes, body colors, and layout (Breakdance uses `!important` heavily and expects to be the only CSS framework)

**Root causes:**

- Breakdance CSS was designed for WordPress, not Next.js/Tailwind
- Turbopack is stricter than browsers — rejects syntax browsers accept
- PostCSS/Tailwind processes globals.css and may transform or strip non-Tailwind CSS
- Breakdance CSS references assets via relative paths (`url(icons/eye.svg)`) that don't exist in the Next.js project
- Breakdance loads custom fonts (Aeonik) via `@font-face` with font files that don't exist in Next.js
- Breakdance CSS variables (`--bde-section-width`, `--bde-column-gap`) are defined in the very file Turbopack rejects

### Goals

1. Clone CSS renders correctly in a Next.js dev server and production build
2. Clone CSS and Tailwind theme tokens coexist — clone CSS handles layout/visual fidelity, Tailwind handles white-label customization
3. The solution is generic — works for any cloned site, not just corvus/colorcode.events
4. The solution integrates into the existing extract-theme pipeline (automated, not manual per-site)
5. Font loading is handled (either clone fonts or graceful fallback)
6. Images from the clone render correctly

### Non-Goals

- Converting Breakdance classes to Tailwind classes (too complex, too brittle)
- Supporting every WordPress plugin's CSS (only the layout/visual CSS that affects rendering)
- Making clone CSS editable via theme tokens (clone CSS is frozen from the reference site)
- Modifying the clone stage (wget + converter) — that works fine
- Modifying the strip pass (content-stripper.ts) — that works fine

### Acceptance Criteria

1. `npx next dev` on the corvus test site (`sites/_corvus-digital-marketing-events/`) renders the homepage with visual fidelity to `output/clones/corvus/html/pages/home.html` opened in a browser
2. `npx next build` succeeds without CSS parser errors
3. `pnpm type-check` passes
4. Tailwind utility classes (`bg-brand-primary`, `text-h1`, etc.) still work in the site alongside clone CSS
5. The extract-theme tool handles CSS preprocessing automatically (no manual steps)
6. Images referenced in clone JSX display correctly
7. Custom fonts either load or gracefully degrade

### Constraints

**Architecture constraints (from CLAUDE.md):**

- Production builds use `next build --webpack` (Turbopack has PostCSS bugs in CI). Turbopack is used for `next dev`.
- Never use CSS `theme()` function in plain CSS files — causes CSS parser panics. Use `var(--custom-property)` instead.
- Never use `packages/themes/**/*.{ext}` glob patterns — causes 18+ minute builds via node_modules descent.
- Theme package filenames: `components/` uses lowercase (`header.tsx`), `pages/` uses PascalCase (`HomePage.tsx`).
- Theme `index.ts` must NOT re-export from `./components` or `./pages` (jiti can't resolve them).
- Site `vercel.json` must NOT set `outputDirectory`.
- Named exports only (no default exports).

**CSS/styling constraints:**

- Always use theme tokens for white-label styling (`bg-brand-primary`, not hardcoded hex)
- No inline styles, no CSS-in-JS — Tailwind only for the platform layer
- Clone CSS is an exception — it's frozen/external CSS that provides the visual skeleton

**Pipeline constraints:**

- Do NOT modify `clone-site.ts`, `scaffold-client-site.ts`, `visual-qa-loop.ts`, or `cpf-validator.ts`
- Do NOT modify live site themes (orion, vega, cygnus, solaris) — only corvus
- The solution must be automated inside `extract-theme.ts` (or a new helper it calls)

### Relevant Architecture

**How working themes load CSS (orion/vega pattern):**

```css
/* packages/themes/orion/globals.css */
@import "../../core-components/src/styles/animations.css";
.btn-primary {
  @apply bg-brand-primary text-white ...;
}
.section {
  @apply py-16 ...;
}
/* Component classes using @apply + Tailwind tokens */
```

```css
/* sites/dj-fox-electrical/app/globals.css */
@import "../../../packages/themes/orion/globals.css";
@tailwind base;
@tailwind components;
@tailwind utilities;
@layer base { ... site-specific overrides ... }
```

The theme `globals.css` contains `@apply`-based component classes (Tailwind-native). The site `globals.css` imports it, then declares `@tailwind base/components/utilities`. Tailwind's PostCSS plugin processes everything together.

**How clone CSS is different:**
The clone `globals.css` contains raw Breakdance CSS (not `@apply`, not Tailwind-aware). It's ~370KB of concatenated WordPress CSS with Breakdance-specific selectors, CSS variables, and font references. This CSS must bypass PostCSS/Tailwind processing entirely.

**Current extract-theme.ts `generateGlobalsCss()` function:**

```typescript
function generateGlobalsCss(customProperties: string, cloneCss: string): string {
  return `/* Auto-generated ... */\n@import "../theme-system/dist/base.css";\n\n:root {\n${customProperties}\n}\n\n.container { ... }\n\n/* Clone styles */\n${cloneCss}`;
}
```

The `@import "../theme-system/dist/base.css"` is wrong — this file doesn't exist. Working themes import `../../core-components/src/styles/animations.css`.

### What a Good Plan Should Cover

1. **CSS loading strategy** — How does the clone CSS get into the Next.js page? Via `<link>` tag to a public file? Via a `<style>` block? Via PostCSS? Something else? Must work with both Turbopack (`next dev`) and webpack (`next build`).

2. **CSS preprocessing** — What transformations are needed on the raw clone CSS before it can load? At minimum: strip/rewrite broken `url()` references, handle the font situation, exclude plugin CSS that isn't needed. This should be automated in the pipeline.

3. **Tailwind coexistence** — How do clone CSS and Tailwind theme tokens coexist without conflicts? The clone CSS handles visual fidelity; Tailwind handles white-label customization. `@tailwind base` (Preflight) conflicts with clone CSS — how is this resolved?

4. **Asset handling** — Clone images (91 files) need to be in the right place. Font files need to either be included or gracefully degraded. Where do these go and how are they referenced?

5. **Integration with extract-theme.ts** — The CSS preprocessing and asset copying should be automated. What new function(s) are needed? Where in the pipeline do they run?

6. **Integration with scaffold-client-site.ts** — When a new site is scaffolded from a clone theme, does the CSS/asset setup happen automatically?

7. **Build compatibility** — Must work with both `next dev` (Turbopack) and `next build --webpack`. Must not cause 18+ minute build times.

8. **Generalization** — The solution must work for any cloned site (different CSS frameworks, different asset structures), not just Breakdance/colorcode.events. What assumptions are being made?
