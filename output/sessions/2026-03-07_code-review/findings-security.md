# Security Review Findings

**Reviewer:** cs-security-engineer
**Scope:** API routes (contact, analytics, CSRF token), security headers (next.config.ts), CSRF/rate-limiter/HTML-escape implementations (packages/core-components/src/lib/security/), tools/ scripts for secrets handling, .env files for committed secrets, dependency audit (pnpm audit), showcase site configuration.
**Date:** 2026-03-07

## Summary

The platform has a solid security foundation: CSRF protection with HMAC-signed single-use tokens, HTML escaping on all user inputs in email templates, validated IP extraction, Supabase-backed rate limiting with multi-tenant isolation, and comprehensive security headers (CSP, HSTS, CORP, Permissions-Policy) on all production sites. No hardcoded secrets were found in source code, and `.env.local` files are properly gitignored. The main issues are: 15 dependency vulnerabilities (1 critical), a missing `CSRF_SECRET` entry in the root `.env.example`, the showcase site shipping without any security headers, and a NRQL injection vector in the sync-external-services tool.

## Findings

### [HIGH] SEC-001: 15 Dependency Vulnerabilities Including 1 Critical (fast-xml-parser)
- **File:** `pnpm-lock.yaml` (root)
- **Issue:** `pnpm audit` reports 15 vulnerabilities: 1 critical (fast-xml-parser entity encoding bypass via regex injection in DOCTYPE, GHSA-m7jm-9gc2-mpf2), 12 high (axios DoS via __proto__ in mergeConfig, minimatch ReDoS across multiple versions, rollup arbitrary file write via path traversal, undici insufficient randomness), 1 moderate, 1 low. The critical fast-xml-parser vulnerability is in `@aws-sdk/client-s3 > @aws-sdk/core > @aws-sdk/xml-builder > fast-xml-parser` (>=5.0.0 <5.3.5).
- **Impact:** The critical fast-xml-parser vulnerability could allow entity encoding bypass in XML parsing if the AWS SDK processes untrusted XML input. The rollup path traversal (GHSA-mw96-cpmx-2vgc) affects the build toolchain via vitest. The minimatch ReDoS vulnerabilities could cause denial of service in linting/glob operations.
- **Fix:** Run `pnpm update` to pull patched versions where available. For transitive dependencies that cannot be directly updated, use `pnpm.overrides` in the root `package.json` to force patched versions: `fast-xml-parser >= 5.3.8`, `minimatch >= 3.1.3` / `>= 9.0.6` / `>= 10.2.1`, `rollup >= 4.59.0`, `axios >= 1.13.5`. After overrides, run `pnpm install && pnpm audit` to verify.
- **Effort:** small

### [MEDIUM] SEC-002: CSRF_SECRET Missing from Root .env.example
- **File:** `.env.example` (root, lines 1-110)
- **Issue:** The root `.env.example` does not include `CSRF_SECRET`, although it is referenced in `turbo.json` passthrough and is required by the CSRF implementation in `packages/core-components/src/lib/security/csrf.ts`. The colossus-scaffolding `.env.example` correctly includes it (line 85), but the root template -- which is what developers copy when setting up new sites -- omits it entirely.
- **Impact:** Without `CSRF_SECRET` set in production, the CSRF module falls back to a per-instance random secret that does not persist across serverless cold starts. This means CSRF tokens generated by one Lambda/Edge instance will be rejected by another, causing intermittent 403 errors on contact form submissions in production for any site created from the root template.
- **Fix:** Add a `CSRF_SECRET` entry to the root `.env.example` with the same documentation as in `sites/colossus-scaffolding/.env.example` (lines 81-85). Also add it to `sites/base-template/.env.example` and `sites/dj-fox-electrical/.env.example`.
- **Effort:** trivial

### [MEDIUM] SEC-003: Showcase Site Missing All Security Headers
- **File:** `sites/showcase/next.config.ts` (lines 1-12)
- **Issue:** The showcase site's `next.config.ts` contains only `transpilePackages` and `images` configuration. It has no `headers()` function, meaning it ships with zero security headers: no CSP, no HSTS, no X-Frame-Options, no X-Content-Type-Options, no Referrer-Policy, no CORP, no Permissions-Policy. All other sites (base-template, dj-fox-electrical, colossus-scaffolding) have the full security header set.
- **Impact:** If the showcase site is deployed publicly, it is vulnerable to clickjacking (no X-Frame-Options), MIME-sniffing attacks (no X-Content-Type-Options), and has no XSS mitigations from CSP. Even if only used internally, this sets a bad precedent and could be copied by future sites.
- **Fix:** Add the standard `headers()` function from any of the other sites' `next.config.ts` to `sites/showcase/next.config.ts`. The base-template version is the canonical reference.
- **Effort:** trivial

### [MEDIUM] SEC-004: NRQL Injection in sync-external-services.ts
- **File:** `tools/sync-external-services.ts` (lines 387-428)
- **Issue:** The `fetchNewRelicMetrics` function interpolates the `appName` parameter directly into NRQL query strings without sanitization: `WHERE appName = '${appName}'`. The `appName` value comes from the Supabase registry (`site.newrelic_app_id`), which is a trusted data source, but the lack of input sanitization means that if the registry data is ever compromised or a developer passes an untrusted value, an attacker could inject arbitrary NRQL clauses to exfiltrate data from the NewRelic account.
- **Impact:** If the Supabase registry is compromised, an attacker could craft a malicious `newrelic_app_id` value to execute arbitrary NRQL queries against the NewRelic account, potentially accessing metrics, events, and sensitive application data from other applications in the same account.
- **Fix:** Sanitize the `appName` parameter by stripping single quotes and special characters before interpolation, or use a parameterized query approach if the NewRelic GraphQL API supports it. At minimum, validate that `appName` matches an expected pattern (alphanumeric, hyphens, underscores only): `if (!/^[a-zA-Z0-9_-]+$/.test(appName)) throw new Error('Invalid app name');`
- **Effort:** trivial

### [MEDIUM] SEC-005: Analytics Track Endpoint Lacks CSRF Protection
- **File:** `sites/base-template/app/api/analytics/track/route.ts` (lines 49-268), `sites/colossus-scaffolding/app/api/analytics/track/route.ts` (lines 49-268)
- **Issue:** The `/api/analytics/track` POST endpoint does not validate a CSRF token. While the contact form endpoints correctly call `validateCsrfToken(request)`, the analytics track endpoint skips this check entirely. The endpoint accepts arbitrary event data via POST and forwards it to GA4, Facebook, and Google Ads APIs.
- **Impact:** An attacker could forge cross-origin POST requests to the analytics endpoint, injecting fake analytics events (page views, conversions) into GA4/Facebook/Google Ads. This could pollute analytics data, trigger false conversion tracking, and waste ad spend on fabricated conversions. The rate limiter provides some mitigation but does not prevent targeted CSRF attacks.
- **Fix:** Add CSRF token validation to the analytics track endpoint, or alternatively, validate the `Origin`/`Referer` header to ensure requests originate from the same site. Given that analytics events are fired from client-side JavaScript, the CSRF token approach used by the contact form would work here too.
- **Effort:** small

### [LOW] SEC-006: Email Subject Line Not HTML-Escaped in Colossus Contact Route
- **File:** `sites/colossus-scaffolding/app/api/contact/route.tsx` (lines 143-146)
- **Issue:** The `emailSubject` variable is constructed from user inputs (`name`, `service`, `location`) without HTML escaping: `const emailSubject = subject || \`New enquiry from ${name}${service ? \` - ${service}\` : ""}...\``. While the email body uses `safeInputs` (escaped values), the subject line uses raw values. Email subjects are generally plain text and not rendered as HTML, but some email clients may interpret certain characters in subjects.
- **Impact:** Minimal real-world risk since email subjects are typically rendered as plain text. However, this is inconsistent with the escaping applied to the email body, and some legacy email clients or notification systems might interpret subject content differently.
- **Fix:** Use `escapeHtml(name)`, `escapeHtml(service)`, and `escapeHtml(location)` when constructing the `emailSubject` string, for defense-in-depth consistency with the body escaping.
- **Effort:** trivial

### [LOW] SEC-007: CSRF Token Replay Protection Uses In-Memory Set (Not Distributed)
- **File:** `packages/core-components/src/lib/security/csrf.ts` (lines 53-71)
- **Issue:** The single-use token enforcement uses an in-memory `Set<string>` (`usedTokens`). In a serverless environment (Vercel), each Lambda instance has its own memory space. A CSRF token used on one instance will not be tracked as "used" on another instance, allowing the same token to be replayed across different instances within its validity window.
- **Impact:** An attacker who intercepts a valid CSRF token could replay it against a different serverless instance. The 1-hour expiration and the fact that tokens are per-session limit the practical exploitation window, but this does weaken the single-use guarantee.
- **Fix:** For full single-use enforcement in a distributed serverless environment, token tracking would need to use Supabase or another shared store (similar to the rate limiter). However, given the low practical risk (tokens are scoped, short-lived, and require interception), this is acceptable as-is with documentation noting the limitation. Add a code comment explaining the serverless constraint.
- **Effort:** medium (if implementing distributed tracking) / trivial (if adding documentation)

### [LOW] SEC-008: Analytics Debug Endpoint Returns Error Details in Non-Development
- **File:** `sites/base-template/app/api/analytics/debug/route.ts` (lines 100-108), `sites/colossus-scaffolding/app/api/analytics/debug/route.ts` (lines 100-108)
- **Issue:** While the GET and POST handlers correctly check `process.env.NODE_ENV !== "development"` and return 404, the error catch blocks in both handlers include `error.message` in the response body: `message: error instanceof Error ? error.message : "Unknown error"`. If an unexpected error occurs before the NODE_ENV check (e.g., during request parsing), the error details would leak to the client.
- **Impact:** Minimal, since the NODE_ENV guard runs before any processing. However, if the error occurs in the NODE_ENV check itself (unlikely but theoretically possible), internal error messages could leak to an attacker providing stack trace or configuration information.
- **Fix:** Move the NODE_ENV check outside the try-catch, or ensure the catch block also checks NODE_ENV before including error details in the response.
- **Effort:** trivial
